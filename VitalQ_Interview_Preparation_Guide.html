1 System Architecture & Real-Time WebSockets
Q 03
Why did you choose SignalR WebSockets over Short/Long Polling or Server-Sent Events (SSE)?
Networking Efficiency
Interviewer Intent: Testing knowledge of TCP handshakes, HTTP/1.1 vs HTTP/2 header overhead, bidirectional data transport, and battery/network constraints in hospitals.
  • Severe Overhead of Short Polling: In a hospital with 50 doctor terminals polling every 2 seconds, the backend handles 1,500 requests/minute. Each HTTP request involves TCP/TLS overhead and 1–2 KB of repeated HTTP headers (Cookies, JWT, User-Agent) even when the queue hasn't changed.
  • Limitations of SSE (Server-Sent Events): SSE is strictly half-duplex (server-to-client). While efficient for notifications, client-to-server operations (like a doctor calling the next patient or updating a triage status) must be initiated through separate HTTP POST calls, splitting the transport architecture into two channels.
  • SignalR WebSockets (Full Duplex & Minimal Framing): After the initial HTTP 101 Switching Protocols handshake, a single persistent TCP connection remains open. Messages are transmitted in lightweight frames with only 2 to 10 bytes of framing overhead.
  • Fallback Grace: SignalR transparently falls back to SSE or Long Polling if a restrictive hospital firewall blocks raw WebSocket connections, providing 100% network resilience out of the box.
Q 04
Why did you architect VitalQ as a Modular Monolith instead of Microservices?
System Design
Interviewer Intent: Testing architectural pragmatism. Senior engineers know when NOT to build microservices.

"Microservices are designed to solve organizational scaling problems (100+ engineers across multiple teams), not necessarily performance problems. Introducing microservices into VitalQ would have created unnecessary operational complexity:"

  • Data Consistency & Distributed Transactions: Patient check-in, vital recording, triage acuity scoring, and queue assignment must succeed or fail together. In microservices, this requires complex distributed transaction orchestrators (Saga pattern, outbox tables, compensating transactions) and risks eventual consistency anomalies in life-critical workflows.
  • Sub-Millisecond In-Memory Calls: In our Modular Monolith, the Triage Engine, Queue Service, and Audit Logger communicate through high-performance C# method calls and in-memory events rather than gRPC/REST serialization over network hops.
  • Strict Modular Boundaries: I decoupled modules using 1:1 interfaces (e.g. ITriageService, IQueueService, IAuthService) and separate folders/DTOs. If any individual module (like Notifications or Reporting) ever requires independent horizontal scaling, it can be extracted into an independent microservice with zero code rewriting.
Q 05
Explain Dependency Injection lifetimes in .NET 8. What is a "Captive Dependency" and how did you prevent it?
.NET 8 Core Memory Safety

In .NET 8, the built-in IoC container supports three lifetimes:

  • Transient: Instantiated every time they are requested. Used for lightweight, stateless utilities.
  • Scoped: Instantiated once per incoming HTTP request pipeline. All database contexts (VitalQDbContext) and business services (QueueService) are Scoped.
  • Singleton: Instantiated once at application startup and shared across the entire application lifecycle (e.g. in-memory caches, background task schedulers).
The "Captive Dependency" Danger:
If a Singleton service holds a reference to a Scoped service (e.g., injecting VitalQDbContext into a singleton background worker), the Scoped service is captured and kept alive indefinitely. This causes:
  1. Memory Bloat: EF Core change trackers continuously accumulate entity references without garbage collection.
  2. Thread Concurrency Crash: DbContext is not thread-safe. Parallel requests invoke methods on the singleton simultaneously, causing InvalidOperationException: A second operation was started on this context instance before a previous operation completed.
The VitalQ Solution: In our background workers (like AntiStarvationWorker), we inject IServiceScopeFactory, creating an explicit scope per execution: 
using var scope = _scopeFactory.CreateScope();
var db = scope.ServiceProvider.GetRequiredService<VitalQDbContext>();
// Deterministically disposed when using block exits!

Q 07
What is the "Thundering Herd" 401 race condition, and why is it fatal in modern SPAs with token rotation?
Race Condition JWT Security
Interviewer Intent: Top-tier question testing real-world frontend concurrency, reactive programming, and API security token rotation semantics.

When a doctor opens the dashboard, the Angular app dispatches multiple parallel HTTP requests (e.g. GET /queue, GET /vitals, GET /notifications). If the 60-minute JWT has just expired, all 3 requests hit the server and return 401 Unauthorized at the exact same millisecond.

[Request 1 (401)] ===> POST /api/auth/refresh (Token A) ===> Success: Issues Token B, Revokes Token A [Request 2 (401)] ===> POST /api/auth/refresh (Token A) ===> CRASH! Token A is ALREADY REVOKED! ===> Server detects "Replay Attack" -> Invalids user!

Because secure backend systems implement Refresh Token Rotation (a refresh token can only be used once), Request 2 and Request 3 attempt to refresh with an already-revoked token. The backend flags this as a replay attack and terminates the user's session, logging the doctor out mid-shift!

Q 08
Walk me through your RxJS shareReplay Mutex Lock implementation in the Angular AuthInterceptor.
RxJS Mutex Angular 19

To prevent parallel refresh requests, we implement a software mutex inside the Angular HttpInterceptor using a BehaviorSubject lock: 

@Injectable()
export class AuthInterceptor implements HttpInterceptor {
  private isRefreshing = false;
  private refreshTokenSubject = new BehaviorSubject<string | null>(null);

  intercept(req: HttpRequest<any>, next: HttpHandler): Observable<HttpEvent<any>> {
    return next.handle(this.addToken(req)).pipe(
      catchError(error => {
        if (error instanceof HttpErrorResponse && error.status === 401) {
          return this.handle401Error(req, next);
        }
        return throwError(() => error);
      })
    );
  }

  private handle401Error(req: HttpRequest<any>, next: HttpHandler): Observable<HttpEvent<any>> {
    if (!this.isRefreshing) {
      // 1. Thread 1 acquires the lock
      this.isRefreshing = true;
      this.refreshTokenSubject.next(null); // Clear previous emissions

      return this.authService.refreshToken().pipe(
        switchMap((newToken: string) => {
          this.isRefreshing = false;
          this.refreshTokenSubject.next(newToken); // 2. Release lock & broadcast new token
          return next.handle(this.addToken(req, newToken));
        }),
        catchError(err => {
          this.isRefreshing = false;
          this.authService.forceLogout();
          return throwError(() => err);
        })
      );
    } else {
      // 3. Threads 2, 3, 4 wait on the BehaviorSubject until the new token is emitted
      return this.refreshTokenSubject.pipe(
        filter(token => token !== null), // Gatekeeper: hold until token arrives
        take(1),                         // Unsubscribe immediately after receiving token
        switchMap(token => next.handle(this.addToken(req, token!))) // Re-dispatch original request
      );
    }
  }
}
Key RxJS Mechanics to highlight:
- filter(token => token !== null) acts as the gate barrier, keeping secondary requests paused until the primary refresh completes.
- take(1) completes the waiting observable after one emission, preventing memory leaks and duplicate executions.
Q 09
How does your custom X-VitalQ-Retry header prevent catastrophic infinite redirect loops?
Defensive Coding Angular

If a user's account is suspended or the refresh token itself has expired, the re-dispatched request will fail with 401 Unauthorized a second time. Without a guard, this triggers another refresh cycle, entering an infinite recursion loop that floods the browser with hundreds of requests and freezes the tab.

The Defense: Before re-dispatching any retried request, we clone it with a custom header: 

const retriedReq = req.clone({
  setHeaders: {
    Authorization: `Bearer ${newToken}`,
    'X-VitalQ-Retry': 'true'
  }
});

At the top of the 401 error handler: if (req.headers.has('X-VitalQ-Retry')) { this.authService.forceLogout(); return throwError(() => error); }. If a request stamped with this header fails with 401, it is immediately aborted and the user is cleanly navigated to the login screen.

Q 10
Why should you never use .Result or .Wait() on C# asynchronous Tasks?
.NET Async Deadlock Prevention
  • ThreadPool Starvation: .Result or .Wait() turns an asynchronous non-blocking operation into a blocking one. The thread handling the request is held idle waiting for the I/O completion port. Under heavy hospital load, all ThreadPool worker threads become tied up waiting, leading to request queueing and severe latency spikes.
  • Deadlock on SynchronizationContext: In environments with a captured SynchronizationContext, the continuation after an await must run on the original thread. If that thread is synchronously blocked on .Result, the continuation cannot execute because the thread is waiting on itself — resulting in a permanent deadlock!
  • Clean Exception Unwinding: await automatically unwraps exceptions to their base type, whereas .Result packages them inside an AggregateException, obscuring root-cause analysis in logs.
3 Database Architecture & SQL Server High-Performance Indexing
Q 11
Explain the difference between a Clustered Index, Non-Clustered Index, and a Filtered Index.
SQL Server Index Internals
  • Clustered Index: Dictates the physical layout of table rows on disk pages. A table can possess only one clustered index (typically Primary Key Id). The leaf pages of the B-tree are the actual data rows.
  • Non-Clustered Index: A separate B-tree structure. Leaf pages contain only the indexed key columns plus a pointer (Clustered Index Key or Row ID) back to the actual data row.
  • Filtered Index: A non-clustered index configured with a WHERE clause. SQL Server indexes only the subset of rows that satisfy the filter expression.
Q 12
Walk me through your Filtered Index on Users.RefreshToken. What are its exact storage and I/O advantages?
SQL Server High Impact

In VitalQ, refresh token lookup occurs on every token refresh request:

CREATE NONCLUSTERED INDEX [IX_Users_RefreshToken]
ON [dbo].[Users] ([RefreshToken])
WHERE [RefreshToken] IS NOT NULL;

The Architectural Advantages:

  1. 99% Smaller Index Footprint: In a hospital user database of 10,000 accounts (doctors, nurses, admins, inactive staff), only ~50 users have an active logged-in session with a valid refresh token at any given moment. 9,950 rows are NULL. A standard index would index all 10,000 rows. Our filtered index stores only the ~50 active records!
  2. Buffer Pool Cache Residency: Because the index is only a few kilobytes, SQL Server keeps the entire B-tree permanently pinned in RAM buffer pool memory. Lookups resolve in sub-millisecond B-tree seeks with zero physical disk reads.
  3. Zero Write-Amplification on Profile Updates: When inactive users update passwords, profile photos, or contact info, SQL Server skips updating IX_Users_RefreshToken entirely because their rows do not meet the filter predicate!
Q 13
What is a Composite Covering Index, and how does the INCLUDE clause eliminate Key Lookups?
SQL Server Query Plan Tuning

When a query selects columns not present in a non-clustered index, SQL Server traverses the index to find the matching keys, and must then perform an expensive Key Lookup (Bookmark Lookup) back to the clustered index disk pages for each row to retrieve the remaining columns.

The Covering Index Solution in VitalQ:

CREATE NONCLUSTERED INDEX [IX_QueueEntries_Status_Priority]
ON [dbo].[QueueEntries] ([DepartmentId], [Status], [PriorityScore] DESC)
INCLUDE ([PatientId], [TokenNumber], [CheckInTime], [EstimatedWaitMinutes]);
  • Key Columns (B-tree navigation): DepartmentId, Status, and PriorityScore are stored in the branch and leaf nodes, enabling fast range seeks and sorted scans.
  • Included Columns (Leaf-level payload): PatientId, TokenNumber, etc., are stored only at the leaf level. They do not increase the height of the B-tree or impose indexing overhead.
  • Query Plan Optimization: The query is 100% Covered. SQL Server retrieves every requested field directly from the index leaf pages without touching the underlying table, dropping I/O cost from $O(N)$ random disk seeks to a single sequential index seek.
Q 14
What is SQL Sargability? Provide an example of an unsargable query and its sargable rewrite.
SQL Sargability Performance

SARGable = Search Argument Able. A query is sargable if the SQL Server Query Optimizer can utilize an index seek rather than having to perform a full index/table scan.

Non-Sargable (Destroys Index Seeks):
SELECT * FROM Appointments WHERE YEAR(AppointmentDate) = 2026;
Why? Wrapping the column inside a function forces SQL Server to execute the YEAR() function row-by-row on every record in the table, resulting in an expensive Full Table Scan!
Sargable Rewrite (Enables Index Seek):
SELECT * FROM Appointments WHERE AppointmentDate >= '2026-01-01' AND AppointmentDate < '2027-01-01';
Why? The column is isolated on one side of the comparison operator, allowing the query engine to jump directly to the target range using an index seek.
Q 15
How do you prevent double-booking race conditions when two patients simultaneously book the same slot?
Transactions Data Integrity

1. Pessimistic Locking with UPDLOCK, ROWLOCK:

BEGIN TRANSACTION;

SELECT SlotId, IsBooked 
FROM DoctorSlots WITH (UPDLOCK, ROWLOCK)
WHERE SlotId = @SlotId;

-- If slot is unbooked:
UPDATE DoctorSlots 
SET IsBooked = 1, PatientId = @PatientId 
WHERE SlotId = @SlotId;

COMMIT TRANSACTION;

"The UPDLOCK hint acquires an update lock immediately during the read phase. If another transaction tries to read the same slot with UPDLOCK, it is blocked until the first transaction commits or rolls back, completely preventing double booking."

2. Optimistic Concurrency with RowVersion (EF Core):

Alternatively, add a [Timestamp] byte[] RowVersion column to the entity. When two users submit bookings for the same version, the second update matches 0 rows because the version was incremented, throwing DbUpdateConcurrencyException which the controller handles by notifying the user that the slot was just reserved.

Q 18
Explain the 60-Minute Anti-Starvation Mathematical Aging Loop. Why is a pure priority queue dangerous in healthcare?
Mathematics Background Worker

The Hazard of Pure Priority Queues: If a hospital experiences a continuous stream of Level 2 and Level 3 emergency arrivals, lower-priority patients (Levels 4 and 5) suffer Starvation. A child with a fractured arm might wait 8+ hours without ever reaching the front of the queue.

The Mathematical Aging Formula:

PriorityScore = BaseWeight(CTAS) + (ElapsedMinutes * 2) Where: - CTAS Level 2 BaseWeight = 1,000 - CTAS Level 3 BaseWeight = 500 - CTAS Level 4 BaseWeight = 100 - CTAS Level 5 BaseWeight = 20 - AgingRate = +2 points per minute elapsed

Clinical Dynamics:

  • A Level 4 patient ($Base = 100$) who has waited 200 minutes reaches a score of $100 + (200 \times 2) = 500$.
  • Their priority now equals a newly arriving Level 3 urgent patient, ensuring fair progression through the queue!

Execution in .NET 8:

An AntiStarvationWorker : BackgroundService triggers every 60 seconds. It updates scores in a single batched SQL query: 

UPDATE QueueEntries
SET PriorityScore = BasePriorityScore + (DATEDIFF(MINUTE, CheckInTime, GETUTCDATE()) * 2)
WHERE Status = 'Waiting';
5 Frontend Engineering & Modern Angular 19 Architecture
Q 19
Why Angular 19 Signals instead of traditional RxJS Observables everywhere?
Angular 19 State Reactivity
  • Synchronous, Glitch-Free State: Signals represent synchronous values (e.g. currentQueue = signal<QueueEntry[]>([])). Computed signals (codeRedCount = computed(() => this.currentQueue().filter(q => q.isCodeRed).length)) execute lazily and memoize results.
  • Zero Subscription Leaks: Signals bound in component templates automatically track dependencies. There is no need for ngOnDestroy unsubscribe logic, takeUntilDestroyed(), or async pipes for standard UI state.
  • When to keep RxJS: RxJS remains the gold standard for asynchronous events and streams — such as WebSocket message streams, search input debouncing (debounceTime), and HTTP error recovery. We use toSignal() to bridge streams into the UI state layer cleanly.
Q 20
How does ChangeDetectionStrategy.OnPush optimize rendering performance in real-time dashboards?
Change Detection 60 FPS

In default change detection, Zone.js triggers a top-to-bottom check of the entire component tree on every single browser event (clicks, timers, microtasks, WebSocket frames). In a busy dashboard with 100 components receiving continuous SignalR updates, this causes heavy CPU load and UI lag.

With ChangeDetectionStrategy.OnPush, Angular skips evaluating a component and its children unless:

  1. An @Input() reference changes by identity (prev !== curr).
  2. An event handler inside the component itself is fired.
  3. A bound Angular Signal emits a new value.
  4. ChangeDetectorRef.markForCheck() is explicitly called.

"This reduced dirty-checking passes by over 85%, ensuring smooth 60 FPS rendering on doctor workstations."

Q 21
Why did you use NgZone.runOutsideAngular for the HIPAA 15-minute idle watcher?
Zone.js HIPAA

To comply with HIPAA auto-lock requirements, the frontend must monitor user activity (mousemove, keydown, scroll).

Because Zone.js monkey-patches all DOM events, attaching a mousemove listener inside the Angular zone causes Angular to run a full application change detection cycle on every single pixel of mouse movement!

The Optimization:

constructor(private ngZone: NgZone, private authService: AuthService) {
  this.ngZone.runOutsideAngular(() => {
    // Zero change detection cycles triggered during movement
    fromEvent(window, 'mousemove').pipe(throttleTime(1000)).subscribe(() => this.resetTimer());
    fromEvent(window, 'keydown').pipe(throttleTime(1000)).subscribe(() => this.resetTimer());
  });
}

private triggerLockout() {
  // Only re-enter the Angular Zone when we actually need to display the lock modal
  this.ngZone.run(() => {
    this.authService.lockSession();
  });
}
Q 22
What was the CSS Transform Modal Trapping bug and how did TeleportToBodyDirective resolve it?
CSS Stacking DOM Portal

Under W3C CSS specifications, applying a CSS transform, filter, or perspective to an element creates a new Containing Block for all descendants.

If a parent card uses a hover animation (e.g. transform: translateY(-2px)), any modal inside it with position: fixed; inset: 0; is trapped inside that tiny card instead of covering the browser viewport!

The Solution: I authored a custom directive TeleportToBodyDirective. When the modal renders, it physically moves the DOM node to document.body while maintaining component data binding and lifecycle integration, completely escaping the transformed parent container.

6 Security, Authentication & HIPAA Compliance
Q 23
Explain your JWT Authentication architecture. Where are tokens stored and why?
Security OAuth / JWT
  • Access Token (Short-lived, 60 minutes): Stored strictly in browser memory inside a private TypeScript service variable — never in localStorage or sessionStorage.
    • Why? localStorage is vulnerable to Cross-Site Scripting (XSS). Any compromised third-party library or malicious script can execute localStorage.getItem('token') and steal credentials. In-memory storage is unreachable by external scripts.
  • Refresh Token (7 days): Stored inside an HttpOnly, Secure, SameSite=Strict Cookie.
    • HttpOnly prevents JavaScript from reading or altering the token (XSS protection).
    • Secure ensures transmission only across encrypted HTTPS channels.
    • SameSite=Strict stops the browser from attaching the cookie to cross-site requests, completely preventing Cross-Site Request Forgery (CSRF).
Q 24
Why is client-side token deletion on logout insufficient in healthcare environments?
Token Revocation HIPAA

Simply removing tokens from client memory or cookies does not invalidate the cryptographic signature of the token on the server. If an adversary intercepted the token prior to logout, they could continue calling protected endpoints until the token expires.

VitalQ Dual-Revocation on Logout:

  1. Server Database Invalidation: POST /api/auth/logout executes: 
    UPDATE Users 
SET RefreshToken = NULL, RefreshTokenExpiry = NULL 
WHERE Id = @UserId;
  2. Cookie Invalidation: Sends an expired cookie header: Set-Cookie: refreshToken=; Path=/; Expires=Thu, 01 Jan 1970 00:00:00 GMT; HttpOnly; Secure.
  3. SignalR Termination: Closes the active WebSocket connection on the server and removes the user from all department broadcast groups.

    "To solve this, I designed an RxJS software mutex inside the Angular AuthInterceptor using a BehaviorSubject. The first 401 request acquires the lock and initiates the refresh call, while subsequent concurrent requests queue on the BehaviorSubject. Once the new token arrives, all queued requests are re-dispatched simultaneously. I also stamped retried requests with a custom X-VitalQ-Retry header to eliminate infinite recursion risks."
  • Result: "The race condition was 100% eliminated. Under automated testing with 50 concurrent requests hitting an expired token, all requests refreshed silently with zero dropped sessions and no disruption to doctor workflows."
Q 28
"If you had to scale VitalQ to handle 100 hospitals across the state with 500,000 daily patients, what would you change in the architecture?"
System Design Scaling 10x
  1. SignalR Backplane with Redis Pub/Sub:
    • When running across a cluster of 10 load-balanced backend servers, a doctor connected to Server 1 would miss emergency alerts generated by a nurse connected to Server 2.
    • Introducing Redis Pub/Sub as a SignalR Backplane ensures real-time messages are broadcast across all server nodes seamlessly.
  2. CQRS & Database Read Replicas:
    • Separate Read and Write workloads. Triage vital insertions and queue bookings write to the SQL Server Primary node.
    • Queue display boards, patient status lookups, and reporting dashboards query Read-Only Replicas (using SQL Server Always On Availability Groups), reducing primary database CPU load by 70%.
  3. Asynchronous Message Queues (RabbitMQ / Azure Service Bus):
    • Offload non-critical side effects (audit logging, WhatsApp/SMS token notifications, and CTAS aging loop updates) into background message queues for asynchronous processing.
  4. Multi-Tenant Table Partitioning:
    • Partition large tables (QueueEntries, TriageAssessments) by HospitalId using SQL Server Table Partitioning, ensuring queries scan only the relevant hospital's data partition.

20 Rapid-Fire Technical Interview Questions & Answers Cheat Sheet
Quick Reference
Question The Exact Senior-Level Answer
IEnumerable vs IQueryable? IEnumerable executes in-memory on the server process after fetching all rows. IQueryable builds expression trees translated into SQL, executing filtering directly on the database engine.
What is a CORS pre-flight? An HTTP OPTIONS request automatically sent by the browser before non-simple cross-origin requests to verify allowed methods, headers, and credentials.
Dispose() vs Finalize()? Dispose() is called deterministically by application code (or using block) to free unmanaged resources. Finalize() is called non-deterministically by the Garbage Collector before memory reclamation.
What is an Idempotent HTTP method? A method where multiple identical requests produce the same side-effect on the server as a single request (e.g. GET, PUT, DELETE are idempotent; POST is not).
What is the N+1 query problem? When an ORM executes 1 query to fetch a parent list and then $N$ additional queries to fetch child entities for each parent. Fixed in EF Core using eager loading with .Include() or projection with .Select().
What is Zone.js in Angular? An execution context library that monkey-patches browser asynchronous APIs (timers, events, promises) to notify Angular when to trigger change detection.
What does @for (item of list; track item.id) do? Provides Angular with a unique identity for each DOM element, allowing it to move or update only changed DOM nodes rather than rebuilding the entire list.
What is the difference between Task.Run and async I/O? Task.Run offloads CPU-bound computation to a background ThreadPool thread. Async I/O (like SaveChangesAsync()) uses non-blocking I/O completion ports with zero active thread consumption.
What is an SQL Deadlock? When two concurrent transactions each hold a lock the other needs to proceed, creating a cycle. SQL Server resolves this by choosing one transaction as the deadlock victim and rolling it back.
What is Content Security Policy (CSP)? An HTTP response header that restricts the resources (scripts, styles, images) the browser is allowed to load for a given page, neutralizing XSS attacks.
